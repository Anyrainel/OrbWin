## Credential and fixture lifetime

Reuse the existing nonce loopback registry, independent manifest/config verification, synthetic public credentials, exact native RegistryLogin/Forget owner, RAM-only two-profile snapshots and ownership-checked restoration under the existing product lock. Do not construct another helper store or copy real credentials. Add a separate opt-in such as `ORBWIN_QUALIFY_COMPOSE_PRIVATE=1`; the receipt must name precisely which client stages ran. Extend the parent's bounded lifetime deliberately if necessary and keep server self-exit and durable pre-mutation intents. Timeout/crash may require exact manual recovery.

Within the authenticated callback, create a new nonce Compose workspace and output image tag, and prove both output tag and private base reference absent from local image references before building. Remove only an already-verified fixture base alias using existing full-ID/nonce ownership checks. Existing base layer blobs/BuildKit records can remain cached: this is an uncached image reference and forced remote metadata/authentication proof, not an empty content-store or transferred-layer proof. Use `build.pull:true`, `build.no_cache:true` and explicit `compose build --pull --no-cache app`; record the exact command and registry lookup evidence. Never call a cached local image inspection equivalent to a private build.

Keep the Dockerfile local under the nonce context, without a remote syntax frontend, package installation, external ADD, mounts or secrets. Its exact FROM is the nonce private reference already verified independently through the registry; a nonce LABEL plus a tiny RUN writes `/orbwin-private-compose-proof`. RUN uses `network:none` and a verified finite BusyBox command. The final CMD must preserve a verified BusyBox timeout around a short sleep (for example120s). A fresh nonce marker and `--no-cache` ensure successful marker verification cannot come from a previous fixture build.

The Compose service uses a nonce output image, explicit nonce container name and qualification labels; no published ports, network mode none, no volumes/binds, readonly root, small nonce tmpfs only if required, user root only inside the fixture, CPU0.25/RAM128MiB/PIDs64/cap-drop ALL/no-new-privileges. No restart policy or healthcheck loop. `compose up --no-build --pull never --detach` starts only this already-built image. Inspect full ID/image/labels/limits/mounts/network, then verify the nonce marker via a bounded exec. Stop and remove that exact ID without broad `down`, force removal or orphan cleanup. The BuildKit build itself is separately bounded by the client wall clock; service limits do not imply BuildKit worker memory/CPU limits. No stress or resource-exhaustion workload is involved.

After actual native Forget, remove only the fixture private base alias if present. Attempt another `compose build --pull --no-cache` against the same private base, with a distinct output tag/nonce marker. It must fail authentication while the registry is still running and an independent unauthenticated registry request still returns401. Verify the negative output tag is absent. If BuildKit retains a usable auth session and succeeds, record a real negative-proof failure, retain ownership receipts, and investigate; do not silently substitute Docker pull failure or alter global builder state to manufacture the expected result.

## BuildKit cache and product metadata accounting

Before build, identify the existing default builder without bootstrap/create/use. `backend-tools/cli/main.go` explicitly binds `BUILDX_BUILDER=default` and the product private `buildx` directory, so a child `BUILDX_CONFIG` override is not an isolation mechanism for this actual-alias proof. Do not introduce a competing builder or change selected defaults. Read-only preparation confirmed the private directory already has activity/defaults/instances/refs/current metadata; that is not evidence that all its bytes may be backed up or rewritten.

Pinned Buildx0.38.1 help supports `du --format`, `du --timeout`, and `history ls --format --no-trunc`. During root's preflight, verify actual JSON output schema without creating/bootstrapping a builder. Parse full records in RAM; persist cache record IDs, bounded numeric sizes/usage and flags only, omitting unrelated descriptions/project paths. Record history references and selected fixture-build references with source/marker relationship; hash rather than dump unrelated history metadata. Unsupported schemas fail cache-accounting qualification instead of inventing counters.

Take before/after BuildKit du/history and `system df` summaries, then report newly seen IDs, removed IDs, changed size/usage flags and retained fixture history. Shared-record sizes are reported API metrics, not independent physical bytes or a guaranteed net-disk delta. Automatic backend GC can change older records; disclose it instead of assigning every delta to the fixture. Never delete cache/history, run prune, reset the builder or remove another workload's image to equalize snapshots.

Whitelist metadata paths before collecting hashes: private Docker config JSON remains exact-restored by the existing owner; Buildx current/default/instance selection metadata must remain unchanged. Buildx activity and fixture ref additions may be expected and must be explicitly listed/hashes accounted for, without reading secret/certificate payloads or retaining config backups. If a pre-existing metadata file changes unexpectedly, preserve it and fail the unchanged-selection claim; do not overwrite current state from a stale snapshot. Ref/activity cache residue may remain after engine fixture cleanup and must appear in the receipt, not be hidden behind `cleaned:true`.

## Review corrections and approved opt-in wiring

The module now verifies Docker's actual `ClientInfo.Plugins` default-discovery metadata in RAM, checks exact discovered Compose/Buildx executable bytes against the current pin, and persists only selected basename/version/hash/provenance. Adjacent staged bytes alone are insufficient. Read-only discovery observed the selected current versions v5.6.1-orbwin.1 and v0.38.1; no full discovered paths are copied into the proof.

Metadata walking validates all ancestor/root/subdirectory nodes using lstat, rejects junctions/symlinks including dangling links, bounds traversal and refuses nonregular selection files. Current/NodeID reads are limited to64KiB plus a one-byte overflow probe, check opened-fd identity before reading and verify path/handle identity and unchanged size/mtime afterward. Windows Node does not expose O_NOFOLLOW; platforms that expose it use it, and Windows uses the identity checks plus repeated ancestor checks. This is not a same-user adversarial filesystem isolation guarantee or a claim of a Windows no-follow syscall. Seven pure tests now pass, including actual Windows junction/dangling-junction/root traversal rejection, oversized metadata and discovered-plugin-path selection.

Root approved minimal opt-in wiring after review: `ORBWIN_QUALIFY_COMPOSE_PRIVATE=1` adds authenticated/forgotten callbacks after the existing client stages; specialized final cleanup precedes generic cleanup. Only new module/tests and the qualification harness changed; production/packaged tools remain untouched. Each Compose operation is bounded90s, instrumentation30s/log read15s, in addition to existing native client-tree240s, parent Cargo480s and registry600s limits. The outer bounds can end a sequence before every individual command budget expires; receipts/manual recovery apply after interruption. No slow-operation completion guarantee or automatic crash cleanup is implied. Root performs the final source review and exclusively runs the command; this preparation has not executed private Compose builds.

## Successful build with incomplete request observer; corrected observation design

Receipt `artifacts/qualification/orbwin-private-client-51d1c085e0404f4e8d03b05c4c64fde1/state.json` records a real Compose build exit0 but failed acceptance because manifest-success counts did not increase. Cleanup is true. It retained BuildKit changes31→34 du records and25→26 history records. The omitted raw logs cannot be reconstructed after registry cleanup, so this is not retrospectively upgraded to a private-build journey pass.

Exact v3.0.0 [registry wiring](https://github.com/distribution/distribution/blob/v3.0.0/registry/registry.go#L145) installs gorilla CombinedLoggingHandler on stdout when enabled. Its [configuration reference](https://github.com/distribution/distribution/blob/v3.0.0/docs/content/about/configuration.md#accesslog) distinguishes this combined access stream from structured logging on stderr. The previous observer parsed only structured JSON/text and compared only a bare tag URI. That left real access events outside its coverage.

The [v3.0.0 manifest dispatcher](https://github.com/distribution/distribution/blob/v3.0.0/registry/handlers/manifests.go#L39) accepts both tag and digest references for GET/HEAD. The [authorization dispatcher](https://github.com/distribution/distribution/blob/v3.0.0/registry/handlers/app.go#L624) returns after failed authorization rather than following the successful structured-completion branch. These sources justify observing combined access records and known-digest/query forms; they do not prove which missing format the removed fixture actually emitted.

The corrected observer accepts Docker-timestamp-prefixed combined access lines plus structured JSON/text. It records only recognized HTTP method/status, source format, query-present boolean and fixed path classifications for the exact fixture repository: nonce manifest tag, independently known manifest digest, other manifest reference or blob/other repository endpoint. Registry-base pings are diagnostic only. Only GET/HEAD for the exact nonce tag or independently verified manifest digest can satisfy the evidence gate; arbitrary tags/digests, other repositories, suffix paths, malformed records and base pings cannot. Full URI/query values, auth headers, usernames, user agents, referrers and raw lines are never serialized.

Before/after snapshots retain the sanitized observations even if the gate fails. After build, at most five log-only reads (2s each) with four150ms waits accommodate log flushing; the observer does not issue registry requests that could manufacture success/refusal evidence. Missing evidence has explicit `NO_MANIFEST_SUCCESS_EVIDENCE`/`NO_MANIFEST_REFUSAL_EVIDENCE` classification; a saturated log window is a separate error. Counts describe log observations and may include separate structured/access records of one request, not a claim of unique HTTP request counts. The async stage is awaited by both main callbacks. Ten pure tests cover the added formats/known-digest/query filtering, sanitization and delayed log-only observation. No new fixture/private build was run for this correction; root reviews the concrete changes before another exclusive attempt.
