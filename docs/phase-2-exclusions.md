# Phase 2 exclusions, deferrals and retained adaptations

Recorded 2026-10-25 for P2-D07e. Authority: current [scope](phase-2-scope.md), [project decisions](project-decisions.md), [quality standard](quality-standard.md), repository instructions and the evidence-qualified [additional-flow review](verification/orbstack-additional-flows/lifecycle-cli-and-exclusions.md). This record accounts for boundaries already stated there. It does not authorize dropping an in-scope journey or convert an implementation/qualification gap into an exclusion.

“Excluded” means outside the accepted product/supported Phase 2 envelope. “Deferred” means a named later evaluation with a trigger and no current support promise. “Adaptation” means the user outcome still needs a real supported implementation and evidence. Documented upstream capability, original OrbWin design, development proof and installed qualification remain different evidence levels.

## Explicit exclusions

| Scope item | Reason/boundary | User impact and alternative outcome | Revisit condition |
| --- | --- | --- | --- |
| Linux machine creation, cloud-init lifecycle, clone/import/export, per-machine allocation, built-in machine SSH | User distributions remain independent; no second WSL manager around rdd | Manage distributions with Microsoft/WSL tools. OrbWin's selected-distro project/client/editor integration remains in scope; it is not machine management | Concrete developer need that cannot be served by selected-distro integration, accepted architecture and ownership/data-safety proof |
| USB, webcams/audio/sound, GPU pass-through | Outside Windows Linux server/service-development Phase 2; no custom drivers/kernel/hypervisor | No OrbWin device management or GPU-support promise. Platform capabilities are not certified merely because WSL exposes them | Phase 4 device evaluation on demand, using supported Microsoft/upstream facilities with hardware-specific evidence |
| Podman backend/UI | Docker/Moby is the selected ecosystem; avoid another lifecycle/store authority | Podman users retain independent tools/data; no migration/interchange promise | Explicit product decision for another backend, compatibility and data-isolation design |
| Docker Extensions | Separate ecosystem/UI/security/dependency scope | No Extensions installation or management in OrbWin | Reviewed demand, supported API/licensing/distribution model and isolation contract |
| Docker Scout product integration | Vendor-specific product is not the accepted engine/UI scope | No integrated Scout subscription/scanning promise; independently invoked scanners need their own compatibility evidence | Explicit supported scanner integration and credential/network/privacy review |
| Direct container-IP access and L2/bridged routes | Owned localhost publication and explicit network selection are the supported model; coexistence must be retained | Use published loopback ports/local service routing. macvlan/ipvlan/direct-IP parity is not implied | Accepted routing architecture, conflict/VPN/firewall/security and three-engine evidence |
| Host-to-container `--net host` bridging | Host-network parity is outside the selected upstream/Windows publication contract | UI Run rejects host network. Use bridge networks and explicit published ports | Supported upstream Windows/WSL implementation with measured isolation/coexistence behavior |
| Arbitrary `.local` suffixes/namespaces | Local names/trust require a constrained owned authority | No arbitrary namespace takeover. Exact names within the approved OrbWin namespace still belong to the in-scope names/HTTPS flow | Namespace/collision/mDNS/client trust review and constrained-signer proof |
| Default CA injection into every container | Workload trust is owned by the workload; global injection weakens consent and reproducibility | Workloads do not automatically trust OrbWin's CA. Windows/WSL and explicitly selected workload/cluster client trust must be accounted separately | Explicit per-client opt-in design, provenance/removal/renewal and enterprise-policy evidence |
| An OrbWin SSH-agent socket or silent credential forwarding | Windows/WSL/SSH already own agents; do not silently broaden credential access | No product-owned agent socket or automatic key forwarding. User-invoked editor/SSH workflows keep their own explicit credential boundary | Concrete gap, supported upstream transport, consent/lifetime/isolation review |
| Compose `dns:` set to a container name | A service/container name is not a numeric resolver configuration; no transparent custom resolver is promised | Use normal selected-network service discovery and supported resolver settings. Cross-project network selection/routing remains in scope | Real supported resolver contract, failure/security behavior and client qualification |

The wider P2-D07 architecture boundary also excludes a custom hypervisor, kernel/chipset drivers, Apple-specific acceleration parity, arbitrary VM management and remote fleet management. They are not prerequisites for supported Docker-dependent server/service work. This does not exclude ordinary container functionality inherited from Docker; unsupported UI/product integration and upstream CLI acceptance are different claims.

## Work that cannot be relabelled excluded

Compose setup/use/build/private-pull/error/cancel/restart/removal; names/HTTPS and multiple exact names/port overrides; files and Debug Shell; WSL and editor integration; portable project/image/volume transfer and migration; activity/capacity/size/pause/platform UI; network/run choices; Dev Containers; opt-in LAN exposure with consent/removal; and the required D01–D07 decisions remain subject to their actual scope acceptance. D08–D11 and every additional flow must also be reconciled. Known implementation gaps, untested privileged operations, an unavailable test machine, expired evidence or the convenience of a passing subset do not authorize a new exclusion.

The final acceptance record must map each in-scope outcome to current installed evidence and each retained boundary above to user-visible explanation. Record unresolved items as open, not complete. Revisit deferrals when their triggers occur or a pin changes the behavior; do not assume this record grants future implementation or external-action permission.
