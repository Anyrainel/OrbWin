# Inventory sorting and creation options

The Docker daemon owns networks, container policies and image metadata. Forms prepare one explicitly targeted Docker CLI request through the existing operation owner; closing/cancelling stops the client and cannot roll back an already accepted create/run. No automatic retry, engine restart or global configuration mutation is introduced. A failed create leaves the reviewed fields available and the daemon conflict diagnostic visible.

Network creation supports the built-in bridge driver, an optional canonical IPv4 CIDR and internal isolation. Other drivers need their own qualified platform envelope. Subnet overlaps and name conflicts remain authoritative daemon errors; preflight cannot reserve a subnet. Run accepts an explicit existing network name (or Docker's default bridge when blank), and a closed restart-policy vocabulary. Neither flow adds privileged/host-network settings.

Size sorting puts measured/parseable sizes first, largest or smallest as selected, and unknown values last in either direction. Image list sizes are Docker's rounded displayed image sizes, not reclaimable disk space. Volume size reads remain opt-in through the existing bounded cancellable API. Measurements retained in the list are in-memory observations, discarded on inventory refresh; failed/cancelled reads never manufacture zero. No background volume scans are added.

Platform badges use inspected image OS/architecture only. Native linux/amd64 is the qualified execution envelope in D07c; other inspected platforms are labelled unsupported, never emulated. Uninspected images remain unverified. Reading metadata does not pull or execute an image.

The bridge-only driver selector is an explicit supported-scope decision: overlay requires the deferred Swarm envelope; macvlan/ipvlan direct container IP and L2 routing are excluded by P2-D07e; host networking bypasses the selected bridge/localhost model. None is a predefined disconnected network, not a new network driver offered here. This is an OrbWin qualification boundary, not a claim that upstream Docker lacks other drivers. Existing network suggestions are an explicit bounded inventory read, filtered to local bridge networks. Cancel discards the result; the existing native read remains bounded by its owner. Names stay editable and Docker checks the submitted network at execution time.

Verification performed for this implementation: TypeScript compilation; 13 focused model/persistence/size regressions; one native Rust pure operation-planning test covering option forwarding, canonical subnet/driver/policy rejection, argument boundaries and default compatibility. No engine changes or native UI runs were used by this task.

## P2-D10: resource-limit scope

Decision: keep engine/WSL allocation read-only and implement explicit per-container constraints. BL-006's requested guest CPU/RAM values are not proof of independent allocation. This flow never edits `.wslconfig`, engine-wide cgroups, host settings or another engine. Existing requested/effective engine views remain authoritative observations with their existing qualification limits.

Docker documents dynamic Linux container updates, CPU quotas and hard RAM constraints in [container update](https://docs.docker.com/reference/cli/docker/container/update/) and [resource constraints](https://docs.docker.com/engine/containers/resource_constraints/) (reviewed 2026-10-25). CPU quota throttles available execution; it is not a reservation. Hard RAM limits can cause OOM termination. Kernel support is required. Docker owns default swap behavior; an existing swap setting may cause an incompatible RAM update to refuse. These upstream descriptions are distinct from installed OrbWin enforcement evidence, which remains a qualification gate.

Run accepts blank/default or positive CPU limits 0.01–1024 with up to three decimal places and positive whole-MiB RAM limits 6–1048576. Inputs are bounded decimal strings, converted to standard `--cpus` and byte-valued `--memory` arguments without a shell. Invalid/zero/nonfinite/exponential/unit-suffixed values refuse before spawning; they are not dropped or coerced into defaults. The validation ceiling is an input bound, not a capacity promise. Blank Run fields omit the flags.

Existing-container changes require an explicit exact-full-ID inspect review in the UI. The bounded read shows reported NanoCPUs, CFS quota/period, RAM and swap, distinguishing absent values from zero/unlimited sentinels. These are Docker configuration values, not measured enforcement or available host capacity. Cancellation/refresh prevents an old read becoming a current review. The confirmed update targets one immutable ID, changes only positive entered fields and leaves blanks unchanged. Both blank refuses. Removing limits/zero is intentionally not offered by this limited editor. No swap tuning, restart, OOM-killer disablement, automatic retry or rollback is introduced. Other clients can change settings concurrently; the review is not a reservation or compare-and-swap. Compose recreation can replace direct edits. Partial acceptance/client loss is handled by the existing operation owner: refresh/inspect before retrying.

Pure evidence: TypeScript compilation; parser checks for exact-ID binding, absent/zero/-1 counters and malformed/unsafe counters; native Rust plan checks of resource boundaries, Run forwarding, positive-only partial updates, empty-update refusal and full-ID targeting. Real enforcement is not established by these tests.

Root-owned D10 qualification: inspect nonce Run CPU/RAM settings; read guest cgroup quota/limit; exercise bounded CPU stress and a fixture-scoped memory/OOM workload; update a running fixture without restart and verify changed values/behavior; verify unchanged blank field, existing swap conflict refusal, concurrent changes and client cancellation/accepted-result uncertainty; recreate a fixture under Compose to establish source-configuration ownership; confirm all global WSL settings/config bytes, engine identities and unrelated workloads unchanged. Native keyboard/layout checks must cover read/cancel/failure, confirmation, editable validation errors, OOM wording and current-versus-stale review. BL-006 is not declared closed by this implementation alone.

## Dedicated production-adapter fixture qualification

Prepared (not executed by the implementing agent): `scripts/qualify-inventory-options.mjs` orchestrates `operations_inventory_qualification.rs::owned_inventory_network_limits`, an explicitly ignored Rust test registered separately by integration. Every create/run/update/exec/stop/remove goes through the real `operations::run` adapter and its engine/lease/client owner. The script's CLI calls are read-only baseline/inspection of explicitly named engines.

Opt in with `ORBWIN_QUALIFY_OWNED=1`, a reviewed `ORBWIN_QUALIFY_FIXTURE_IMAGE=sha256:FULL_CACHED_ID`, and an unused explicit `ORBWIN_QUALIFY_SUBNET=172.30.X.0/24`. It refuses missing cache/foreign architecture/image-declared volumes and pre-existing owned subnet overlap before dispatch. It does not pull/build an image. Registration, compile and engine execution remain root-controlled; syntax/rustfmt checks alone are not execution evidence.

The wrapper records three engine IDs and container/image/volume/network inventories, container running/paused/restart counters, Docker/kube/private Windows/private WSL/project-record/global WSL hashes, and non-elevation before/after. All fixture names contain a new random 128-bit nonce; Run's explicit environment marker supplies immutable ownership because that production form has no label field. Intent is retained before dispatch. Cleanup verifies exact full ID, name, immutable image, marker, no mounts and stopped state for containers; network cleanup requires exact nonce intent name, local bridge/internal/selected subnet and no attachments. Uncertain or differing objects remain for review; no broad prune/force cleanup is available.

The test verifies bridge/IPAM/internal and name/subnet conflict refusal; four stored restart policies and exact selected network; CPU quota plus observed throttling; partial CPU/RAM update with unchanged blank field/no restart and updated guest cgroup values. It verifies cached BusyBox timeout/awk applets before starting CPU/allocation workloads. A 0.1-CPU/32-MiB RAM fixture arms its finite allocation only after cgroup-v2 RAM32MiB and swap at most32MiB are read. CPU loop and OOM wait/allocation have independent120s/90s BusyBox timeouts if the harness disappears. Forty OOM observations include per-client work and are not advertised as a10s wall-clock deadline; the wrapper has a300s process bound. Abrupt wrapper/test loss can retain stopped/owned fixture resources; the evidence must drive exact manual recovery. Restart-policy fixtures may restart according to their requested policy if the test is lost before explicit Stop, so inspect retained intent rather than claiming automatic rollback.

This fixture does not qualify native form interaction, installed packaging, actual automatic restart backoff semantics, arbitrary subnet/VPN conflicts, resource-limit removal, cgroup-v1, or cancellation of an already accepted update. Those remain separate gates; normal fixture success cannot substitute for them.

## Terminal form and cancellation review (2026-10-25)

The generic operation handler now refuses Enter submission after any terminal result, as well as while a request is active. Previously hiding the submit button did not prevent the form handler from dispatching again after success. Cancel displays a distinct stopping status, disables repeated cancellation, and waits for the client result and state refresh without claiming rollback. A local validation refusal before any backend dispatch can explicitly return to Review inputs with focus on the first field. Backend errors, nonzero exits, timeouts, cancellation, success and refresh failure cannot enable that same-form retry: a refreshed inventory alone cannot prove a non-idempotent Run/Create never committed. Native validation errors currently require closing, inspecting state and opening a fresh reviewed action; structured preflight provenance is needed before offering safer inline native-error retry. Pure retry eligibility tests and the existing metadata cancellation tests pass; the newly changed terminal Enter/stopping/review-focus behavior still requires a native interaction check.
